## Endpoints

| Method and path | Roles | Purpose | Task |
| --- | --- | --- | --- |
| `GET /api/v1/users` | `PORT_GM` (`users.manage`) | Page of users ordered by name; filters `is_active`, `q` (part of the name or username) | P2-E1 |
| `POST /api/v1/users` | `PORT_GM` | Create a user; the one-time password is in this response only | P2-E1 |
| `GET /api/v1/users/{user}` | `PORT_GM` | The user with the active role and the role history, newest first (P-24) | P2-E1 |
| `POST /api/v1/users/{user}/deactivate` | `PORT_GM` | Deactivate; the user is refused on their next request | P2-E1 |
| `POST /api/v1/users/{user}/activate` | `PORT_GM` | Activate again; counts against the plan's user limit | P2-E1 |
| `POST /api/v1/users/{user}/roles` | `PORT_GM` | Give the user a role; the active one is ended and the new one starts in one transaction | P2-E2 |
| `POST /api/v1/users/{user}/roles/end` | `PORT_GM` | End the user's active role; the user is left without a role | P2-E2 |
| `GET /api/v1/users/{user}/devices` | `PORT_GM` (`devices.manage`) | Page of the user's mobile devices, newest first (P-25) | P2-E3 |
| `POST /api/v1/users/{user}/devices/{device}/revoke` | `PORT_GM` | Cancel one device and all its live tokens | P2-E3 |
| `POST /api/v1/users/{user}/devices/revoke-all` | `PORT_GM` | Cancel every device of the user that is not cancelled yet | P2-E3 |
| `POST /api/v1/users/{user}/devices/{device}/restore` | `PORT_GM` | Bring a cancelled device back; its old tokens stay cancelled | P2-E3 |
| `GET /api/v1/audit-logs` | `PORT_GM` (`audit.read`) | Page of audit rows, newest first, with filters; the change history of a master-data record is the same list filtered by `entity_type` and `entity_id` | P2-F8 |

Writes from the web send `X-XSRF-TOKEN` (CT-03). Deactivate, activate, give a role and end a role send the user's `version` as last read; a stale one is 409 `VERSION_CONFLICT`. The four device routes take no body and no `version`.

## Examples

`id`, names and times are examples. `version` is the user's `updated_at` in UTC with microseconds; send it back unchanged.

### POST /api/v1/users → 201

```json
// request
{ "name": "Ahmed Salem", "username": "Ahmed.Salem", "phone": "+20 100 000 0000" }
```

```json
// response (Cache-Control: no-store)
{
  "id": 57,
  "name": "Ahmed Salem",
  "username": "ahmed.salem",
  "phone": "+20 100 000 0000",
  "is_active": true,
  "must_change_password": true,
  "version": "2026-11-21T09:15:02.123456Z",
  "created_at": "2026-11-21T09:15:02.000000Z",
  "active_role": null,
  "one_time_password": "k7XqPm3VwRt9ZbHn4Yc2"
}
```

The username is trimmed and lowercased before validation (3 to 50 characters: letters, digits, `.`, `_`, `-`; unique in any case). The one-time password is never returned again; the user must change it at first sign-in. A new user has no role until the Port Admin gives one (`POST /users/{user}/roles`).

### GET /api/v1/users/{user} → 200

The same fields plus `role_history`: every assignment, newest first, each in the `active_role` shape (`active_to` set on ended ones).

### POST /api/v1/users/{user}/deactivate → 200

```json
// request
{ "version": "2026-11-21T09:15:02.123456Z" }
```

The response is the user with `is_active` false and a new `version`. Activate takes the same body and answers the user with `is_active` true.

### POST /api/v1/users/{user}/roles → 200

```json
// request, a harbour or marine role has no terminal_id
{ "role": "MARINE_PILOT", "version": "2026-11-21T09:15:02.123456Z" }
```

```json
// request, a terminal role needs terminal_id
{ "role": "TERMINAL_OFFICER", "terminal_id": 3, "version": "2026-11-21T09:15:02.123456Z" }
```

The response is the user as in `GET /users/{user}`: the new `active_role`, the old one in `role_history` with `active_to` set (newest first), and a new `version`. A terminal role without `terminal_id`, any other role with one, or a `terminal_id` that has no organization unit is 422 on the field `terminal_id`. Asking for the role the user already has changes nothing: 200, same `version`.

### POST /api/v1/users/{user}/roles/end → 200

```json
// request
{ "version": "2026-11-21T09:15:02.123456Z" }
```

The response is the user with `active_role` null and the history, with a new `version`. The user then gets 403 on every request. A user with no active role: 200, same `version`.

### GET /api/v1/users/{user}/devices → 200

```json
{
  "data": [
    {
      "id": 12,
      "device_id": "a3f9c1e2-5b7d-4c10-9a2e-0d4f6b1c8e77",
      "platform": "ANDROID",
      "app_version": "1.4.2",
      "last_seen_at": "2026-11-21T08:40:11.000000Z",
      "revoked_at": null,
      "has_push_token": true,
      "live_token_count": 1
    }
  ],
  "meta": { "page": 1, "per_page": 25, "total": 1 }
}
```

`device_id` is the app's own id; `id` is the row to use in the other three paths. The push token is never returned: `has_push_token` only says whether one is registered. `live_token_count` counts tokens that are neither cancelled nor expired.

### POST /api/v1/users/{user}/devices/{device}/revoke → 200

No body. The response is the device with `revoked_at` set, `has_push_token` false and `live_token_count` 0. All its live tokens are cancelled in the same transaction: the next Bearer request with one of them is 401, and a new sign-in from that device is 403 `DEVICE_REVOKED`. Cancelling a device that is already cancelled changes nothing: 200. A device of another user addressed under this `{user}` is 404.

### POST /api/v1/users/{user}/devices/revoke-all → 200

```json
{ "devices_revoked": 2, "tokens_revoked": 3 }
```

Every device of the user that was not cancelled gets the same treatment as above. A user with no such device gets zeros. Web sessions are not touched.

### POST /api/v1/users/{user}/devices/{device}/restore → 200

No body. The response is the device with `revoked_at` null, `has_push_token` false and `live_token_count` 0. Tokens cancelled with the device stay cancelled and the push registration stays empty until the app registers it again: the user signs in again, and that sign-in now succeeds (200 instead of 403 `DEVICE_REVOKED`). Restoring a device that is not cancelled changes nothing: 200.

### GET /api/v1/audit-logs → 200

Query (all optional): `page`, `per_page`, `entity_type` (table name, for example `berths`), `entity_id` (use with `entity_type`), `actor_id`, `action`, `from` and `to` (ISO 8601 with `Z` or an offset; a time with no offset is 422; `from` not after `to`), `q` (part of the actor's username or name). Newest first. `action` is one of `CREATE`, `UPDATE`, `DELETE`, `STATUS_CHANGE`, `SAFETY_EXCEPTION`, `REJECTED_ATTEMPT`.

Master-data history is this list with a filter, for example `GET /api/v1/audit-logs?entity_type=berths&entity_id=3`.

```json
{
  "data": [
    {
      "id": 9012,
      "actor": { "id": 41, "name": "Port Admin", "username": "port.admin" },
      "entity_type": "berths",
      "entity_id": 3,
      "action": "UPDATE",
      "before_state": { "name": "Berth 3" },
      "after_state": { "name": "Berth 3 East" },
      "occurred_at": "2026-11-20T14:02:11.000000Z"
    }
  ],
  "meta": { "page": 1, "per_page": 25, "total": 1 }
}
```

`actor` is null for the system or a worker. `before_state` and `after_state` hold the changed fields: a CREATE has no `before_state`, a DELETE no `after_state`. A refused request is a row with `action` `REJECTED_ATTEMPT` and `route`, `status`, `code`, `reason` and `username` in `after_state`. It is a read, so it works in every licence mode.

### Error bodies

All are `application/problem+json`.

```json
// 409 CONFLICT, deactivating yourself. The last active Port Admin (deactivate, replace its role or end it) gives the same code with the detail "At least one active Port Admin must remain."
{
  "type": "https://atlantech.io/errors/conflict",
  "title": "Conflict",
  "status": 409,
  "code": "CONFLICT",
  "message_key": "errors.conflict",
  "detail": "You cannot deactivate your own account."
}
```

```json
// 422 PLAN_LIMIT_EXCEEDED, create or activate above the plan's active-user limit
{
  "type": "https://atlantech.io/errors/plan-limit-exceeded",
  "title": "Plan limit exceeded",
  "status": 422,
  "code": "PLAN_LIMIT_EXCEEDED",
  "message_key": "errors.plan_limit_exceeded",
  "detail": "This would exceed a limit of the port plan. Contact your port administrator."
}
```

409 `VERSION_CONFLICT` carries `current` (`id`, `version`) as in CT-01; 422 `VALIDATION_FAILED` carries `errors`.

## Known gaps

- **Audit log:** only the Port Admin can read it. Rows are never changed or deleted. Events from workers appear with `actor` null. There is no export and no full-text search on the changed values.
- Web sessions of a user are not ended by revoke-all (only mobile tokens); use deactivate to end a user.
- CT-04 (mobile sign-in) is unchanged: after a restore the app signs in again, as CT-04 v1.2 already says it may keep sign-in available.
- The READ_ONLY licence mode is not enforced yet (P2-D5); deactivate will stay allowed in READ_ONLY, create and activate will not.
- Two creates with the same new username at the same moment: the second may answer 500 instead of 422 (rare; logged in the P2-E1 review).
