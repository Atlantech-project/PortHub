## Endpoints

| Method and path | Roles | Purpose | Task |
| --- | --- | --- | --- |
| `GET /api/v1/users` | `PORT_GM` (`users.manage`) | Page of users ordered by name; filters `is_active`, `q` (part of the name or username) | P2-E1 |
| `POST /api/v1/users` | `PORT_GM` | Create a user; the one-time password is in this response only | P2-E1 |
| `GET /api/v1/users/{user}` | `PORT_GM` | The user with the active role and the role history, newest first (P-24) | P2-E1 |
| `POST /api/v1/users/{user}/deactivate` | `PORT_GM` | Deactivate; the user is refused on their next request | P2-E1 |
| `POST /api/v1/users/{user}/activate` | `PORT_GM` | Activate again; counts against the plan's user limit | P2-E1 |
| `POST /api/v1/users/{user}/roles` | `PORT_GM` | Give the user a role; the active one is ended and the new one starts in one transaction | P2-E2 |
| `POST /api/v1/users/{user}/roles/end` | `PORT_GM` | End the user's active role; the user is left without a role | P2-E2 |

Writes from the web send `X-XSRF-TOKEN` (CT-03). Deactivate, activate, give a role and end a role send the user's `version` as last read; a stale one is 409 `VERSION_CONFLICT`.

## Examples

`id`, names and times are examples. `version` is the user's `updated_at` in UTC with microseconds; send it back unchanged.

### Statuses per endpoint

| Endpoint | Success | Errors |
| --- | --- | --- |
| `GET /users` | 200 | 401 · 403 · 422 |
| `POST /users` | 201 | 401 · 403 · 419 · 422 `VALIDATION_FAILED` · 422 `PLAN_LIMIT_EXCEEDED` |
| `GET /users/{user}` | 200 | 401 · 403 · 404 |
| `POST /users/{user}/deactivate` | 200 | 401 · 403 · 404 · 409 `VERSION_CONFLICT` · 409 `CONFLICT` · 419 · 422 |
| `POST /users/{user}/activate` | 200 | 401 · 403 · 404 · 409 `VERSION_CONFLICT` · 419 · 422 `VALIDATION_FAILED` · 422 `PLAN_LIMIT_EXCEEDED` |
| `POST /users/{user}/roles` | 200 | 401 · 403 · 404 · 409 `VERSION_CONFLICT` · 409 `CONFLICT` · 419 · 422 `VALIDATION_FAILED` |
| `POST /users/{user}/roles/end` | 200 | 401 · 403 · 404 · 409 `VERSION_CONFLICT` · 409 `CONFLICT` · 419 · 422 `VALIDATION_FAILED` |

A role other than `PORT_GM` gets 403 before any 404, so a non-admin cannot learn whether an id exists. Deactivating an inactive user, or activating an active one, is 200 with the same `version` and changes nothing.

### POST /api/v1/users → 201

```json
// request
{ "name": "Ahmed Salem", "username": "Ahmed.Salem", "phone": "+20 100 000 0000" }
```

```json
// response (Cache-Control: no-store)
{
  "id": 57,
  "name": "Ahmed Salem",
  "username": "ahmed.salem",
  "phone": "+20 100 000 0000",
  "is_active": true,
  "must_change_password": true,
  "version": "2026-11-21T09:15:02.123456Z",
  "created_at": "2026-11-21T09:15:02.000000Z",
  "active_role": null,
  "one_time_password": "k7XqPm3VwRt9ZbHn4Yc2"
}
```

The username is trimmed and lowercased before validation (3 to 50 characters: letters, digits, `.`, `_`, `-`; unique in any case). The one-time password is never returned again; the user must change it at first sign-in. A new user has no role until the Port Admin gives one (`POST /users/{user}/roles`).


### GET /api/v1/users/{user} → 200

The same fields plus `role_history`: every assignment, newest first, each in the `active_role` shape (`active_to` set on ended ones).

### POST /api/v1/users/{user}/deactivate → 200

```json
// request
{ "version": "2026-11-21T09:15:02.123456Z" }
```

The response is the user with `is_active` false and a new `version`. Activate takes the same body and answers the user with `is_active` true.

### POST /api/v1/users/{user}/roles → 200

```json
// request, a harbour or marine role has no terminal_id
{ "role": "MARINE_PILOT", "version": "2026-11-21T09:15:02.123456Z" }
```

```json
// request, a terminal role needs terminal_id
{ "role": "TERMINAL_OFFICER", "terminal_id": 3, "version": "2026-11-21T09:15:02.123456Z" }
```

The response is the user as in `GET /users/{user}`: the new `active_role`, the old one in `role_history` with `active_to` set (newest first), and a new `version`. A terminal role without `terminal_id`, any other role with one, or a `terminal_id` that has no organization unit is 422 on the field `terminal_id`. Asking for the role the user already has changes nothing: 200, same `version`.

### POST /api/v1/users/{user}/roles/end → 200

```json
// request
{ "version": "2026-11-21T09:15:02.123456Z" }
```

The response is the user with `active_role` null and the history, with a new `version`. The user then gets 403 on every request. A user with no active role: 200, same `version`.

### Error bodies

All are `application/problem+json`.

```json
// 409 CONFLICT, deactivating yourself. The last active Port Admin (deactivate, replace its role or end it) gives the same code with the detail "At least one active Port Admin must remain."
{
  "type": "https://atlantech.io/errors/conflict",
  "title": "Conflict",
  "status": 409,
  "code": "CONFLICT",
  "message_key": "errors.conflict",
  "detail": "You cannot deactivate your own account."
}
```

```json
// 422 PLAN_LIMIT_EXCEEDED, create or activate above the plan's active-user limit
{
  "type": "https://atlantech.io/errors/plan-limit-exceeded",
  "title": "Plan limit exceeded",
  "status": 422,
  "code": "PLAN_LIMIT_EXCEEDED",
  "message_key": "errors.plan_limit_exceeded",
  "detail": "This would exceed a limit of the port plan. Contact your port administrator."
}
```

409 `VERSION_CONFLICT` carries `current` (`id`, `version`) as in CT-01; 422 `VALIDATION_FAILED` carries `errors`.

## Seed data on the dev server

- `FirstPortAdminSeeder` creates the first Port Admin from `FIRST_PORT_ADMIN_USERNAME`, `FIRST_PORT_ADMIN_NAME` and `FIRST_PORT_ADMIN_PASSWORD` in the server's `.env`, only when no active Port Admin exists. The password must be changed at first sign-in.
- Outside production the demo seeders (P1-B6) also create demo users for every role, including `port.gm`.
- No licence row means no user limit.
