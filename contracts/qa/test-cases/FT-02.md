## Detailed Test Cases

### TC-02-001: Web Sign-in with Valid Credentials
- Description: Verify that an active port staff member can authenticate using valid username and password, receiving a stateful Laravel Sanctum session cookie and profile payload.
- Preconditions: Database seeded with active user `staff.ahmed`, role `PORT_STAFF`, password `Secret123!`, `is_active = true`, `must_change_password = false`.
- Test Steps:
  1. Send `GET /sanctum/csrf-cookie` to obtain initial CSRF cookie.
  2. Send `POST /api/v1/auth/login` with header `X-XSRF-TOKEN: <token_value>`.
  3. Payload: `{"username": "staff.ahmed", "password": "Secret123!"}`.
- Expected Result: HTTP 200 OK. Response body contains `id`, `name`, `role: "PORT_STAFF"`, `terminal_ids: []`, `must_change_password: false`. Set-Cookie header contains session identifier.
- Negative / Edge Cases Covered: Validates that username lookup is case-insensitive where configured and whitespace is trimmed.
- Required Evidence: HTTP response headers with Set-Cookie, response JSON body, and application session log.

### TC-02-002: Web Sign-in with Invalid Credentials
- Description: Verify that login attempts with non-existent usernames or incorrect passwords return identical unauthenticated error responses without leaking user existence.
- Preconditions: Database contains user `staff.ahmed`. Nonexistent user `ghost.user` does not exist.
- Test Steps:
  1. Send `POST /api/v1/auth/login` with payload `{"username": "staff.ahmed", "password": "WrongPassword99!"}`.
  2. Send `POST /api/v1/auth/login` with payload `{"username": "ghost.user", "password": "AnyPassword123!"}`.
- Expected Result: HTTP 401 UNAUTHENTICATED for both requests. Response problem JSON: `code = "UNAUTHENTICATED"`, `message_key = "errors.unauthenticated"`, `detail = "The username or password is incorrect."`. No session cookie issued.
- Negative / Edge Cases Covered: Uniform timing and response message preventing user enumeration.
- Required Evidence: HTTP 401 status code and RFC 9457 error body for both attempts.

### TC-02-003: Web Sign-in for Deactivated Account
- Description: Verify that a deactivated account (`is_active = false`) cannot establish a session.
- Preconditions: Database contains user `disabled.staff`, `is_active = false`, password `Secret123!`.
- Test Steps:
  1. Send `POST /api/v1/auth/login` with payload `{"username": "disabled.staff", "password": "Secret123!"}`.
- Expected Result: HTTP 403 ACCOUNT_DISABLED. Problem body: `code = "ACCOUNT_DISABLED"`, `message_key = "errors.account_disabled"`, `detail = "Your account has been disabled. Contact your port administrator."`.
- Negative / Edge Cases Covered: Prevents disabled users from logging in regardless of password correctness.
- Required Evidence: HTTP 403 response payload with stable code `ACCOUNT_DISABLED`.

### TC-02-004: Web Sign-in Missing Required Fields
- Description: Verify that requests missing `username` or `password` fields are rejected with schema validation errors.
- Preconditions: Server is reachable.
- Test Steps:
  1. Send `POST /api/v1/auth/login` with empty JSON body `{}`.
  2. Send `POST /api/v1/auth/login` with `{"username": "staff.ahmed"}` (missing password).
- Expected Result: HTTP 422 VALIDATION_FAILED. Problem body contains `errors.username` or `errors.password` with `validation.required` rule key.
- Negative / Edge Cases Covered: Malformed JSON or null values.
- Required Evidence: HTTP 422 status and errors dictionary.

### TC-02-005: Web Sign-in Rate Limiting
- Description: Verify that brute force login attempts are throttled after consecutive failures from the same IP/account.
- Preconditions: Active user `staff.ahmed`.
- Test Steps:
  1. Send 5 consecutive `POST /api/v1/auth/login` requests with incorrect passwords within 60 seconds.
  2. Send a 6th `POST /api/v1/auth/login` request.
- Expected Result: HTTP 429 TOO_MANY_ATTEMPTS on the 6th request. Response header includes `Retry-After: <seconds>`. Body carries `code = "TOO_MANY_ATTEMPTS"`.
- Negative / Edge Cases Covered: IP-based and username-based combined throttling.
- Required Evidence: HTTP 429 response header `Retry-After` and JSON error body.

### TC-02-006: Fetch User Profile for Active Session
- Description: Verify that `GET /api/v1/auth/me` returns the current user profile when called within an active session.
- Preconditions: Signed-in session established for `staff.ahmed` (`PORT_STAFF`).
- Test Steps:
  1. Send `GET /api/v1/auth/me` with session cookie.
- Expected Result: HTTP 200 OK. Body returns `{ "id": 41, "name": "Port Staff", "role": "PORT_STAFF", "terminal_ids": [], "must_change_password": false }`.
- Negative / Edge Cases Covered: Session validation across requests without re-entering credentials.
- Required Evidence: HTTP 200 response JSON showing profile and role match.

### TC-02-007: Fetch User Profile Without Session
- Description: Verify that calling `GET /api/v1/auth/me` without a valid session cookie returns unauthenticated.
- Preconditions: No session cookie provided or cookie expired.
- Test Steps:
  1. Send `GET /api/v1/auth/me` with no cookies or headers.
- Expected Result: HTTP 401 UNAUTHENTICATED. Body: `code = "UNAUTHENTICATED"`, `message_key = "errors.unauthenticated"`.
- Negative / Edge Cases Covered: Invalid session token, cleared cookies.
- Required Evidence: HTTP 401 status and RFC 9457 error body.

### TC-02-008: Password Gate Enforcement on Protected Routes
- Description: Verify that an authenticated user with `must_change_password = true` is blocked from accessing operational endpoints.
- Preconditions: User `new.user` signed in with one-time password; `must_change_password = true` in database.
- Test Steps:
  1. Authenticate as `new.user`.
  2. Attempt to call a protected route, e.g. `GET /api/v1/users` or `GET /api/v1/berthing-requests`.
- Expected Result: HTTP 403 PASSWORD_CHANGE_REQUIRED. Body: `code = "PASSWORD_CHANGE_REQUIRED"`, `detail = "You must change your password before continuing."`.
- Negative / Edge Cases Covered: Allowed exception routes: `auth/me`, `auth/change-password`, `auth/logout` remain accessible.
- Required Evidence: HTTP 403 status code with `PASSWORD_CHANGE_REQUIRED` code.

### TC-02-009: Forced Password Change with Valid New Password
- Description: Verify that a user can update their password via `POST /api/v1/auth/change-password`, clearing the temporary password requirement.
- Preconditions: Signed-in user with `must_change_password = true`, current password `TempPass123!`.
- Test Steps:
  1. Send `POST /api/v1/auth/change-password`.
  2. Payload: `{"current_password": "TempPass123!", "new_password": "SecurePassword2026!", "new_password_confirmation": "SecurePassword2026!"}`.
- Expected Result: HTTP 200 OK. Body returns user profile with `must_change_password: false`. Database shows password hash updated and `must_change_password` set to 0. Session regenerated.
- Negative / Edge Cases Covered: Immediate authorization to access previously blocked endpoints.
- Required Evidence: HTTP 200 response body and database record snapshot showing flag update.

### TC-02-010: Password Change Reusing Current Password
- Description: Verify that the system rejects a new password identical to the current one.
- Preconditions: Signed-in user with password `CurrentPass123!`.
- Test Steps:
  1. Send `POST /api/v1/auth/change-password` with `{"current_password": "CurrentPass123!", "new_password": "CurrentPass123!", "new_password_confirmation": "CurrentPass123!"}`.
- Expected Result: HTTP 422 VALIDATION_FAILED. Errors dictionary contains `"new_password": ["validation.different"]`.
- Negative / Edge Cases Covered: Password history validation rule preventing identical reset.
- Required Evidence: HTTP 422 error JSON with `validation.different`.

### TC-02-011: Password Change Complexity Violation
- Description: Verify that new passwords failing minimum complexity requirements (<8 chars, only numbers, or only letters) are rejected.
- Preconditions: Signed-in user.
- Test Steps:
  1. Send `POST /api/v1/auth/change-password` with short password: `{"current_password": "OldPass123!", "new_password": "short", "new_password_confirmation": "short"}`.
  2. Send `POST /api/v1/auth/change-password` with mismatched confirmation: `{"current_password": "OldPass123!", "new_password": "NewValidPass123!", "new_password_confirmation": "DifferentPass456!"}`.
- Expected Result: HTTP 422 VALIDATION_FAILED for both cases with `validation.min` and `validation.confirmed` error keys.
- Negative / Edge Cases Covered: Password length, character composition, confirmation mismatch.
- Required Evidence: HTTP 422 responses with validation error arrays.

### TC-02-012: Web Logout Terminates Active Session
- Description: Verify that `POST /api/v1/auth/logout` invalidates the server session and clears authentication cookies.
- Preconditions: Signed-in web session.
- Test Steps:
  1. Send `POST /api/v1/auth/logout` with session cookie and CSRF token.
  2. Verify response status.
  3. Attempt to call `GET /api/v1/auth/me` with the previous session cookie.
- Expected Result: Step 1 returns HTTP 204 No Content with cleared session cookie. Step 3 returns HTTP 401 UNAUTHENTICATED.
- Negative / Edge Cases Covered: Replay attack prevention; session ID invalidated on server storage.
- Required Evidence: HTTP 204 response followed by HTTP 401 on re-use.

### TC-02-013: CSRF Protection for Web Mutating Requests
- Description: Verify that state-changing web requests without a valid CSRF token header (`X-XSRF-TOKEN`) are rejected.
- Preconditions: User signed in via Sanctum web session.
- Test Steps:
  1. Send `POST /api/v1/auth/change-password` omitting the `X-XSRF-TOKEN` header.
- Expected Result: HTTP 419 SESSION_EXPIRED. Response body: `code = "SESSION_EXPIRED"`, `message_key = "errors.session_expired"`.
- Negative / Edge Cases Covered: Cross-Site Request Forgery attempt mitigation.
- Required Evidence: HTTP 419 error response body.

### TC-02-014: Mobile Tablet Sign-in with Device Headers
- Description: Verify that field users can authenticate from tablet devices via `POST /api/v1/auth/mobile/login`, sending device metadata and receiving a 30-day sliding Bearer token.
- Preconditions: User `pilot.tarek` active with role `PILOT`, password `PilotPass123!`.
- Test Steps:
  1. Send `POST /api/v1/auth/mobile/login`.
  2. Headers: `X-Device-Id: TAB-DAM-0042`, `X-App-Version: 2.4.0`.
  3. Payload: `{"username": "pilot.tarek", "password": "PilotPass123!", "platform": "ANDROID"}`.
- Expected Result: HTTP 200 OK. Response body contains `token` (Bearer string), `expires_at` (30 days in future UTC), `user: { id, name, role: "PILOT", terminal_ids: [] }`. Table `user_devices` records device ID, platform, last active timestamp.
- Negative / Edge Cases Covered: Sliding window renewal upon subsequent mobile activity.
- Required Evidence: HTTP 200 JSON body and `user_devices` database row verification.

### TC-02-015: Mobile Sign-in with Outdated Client App Version
- Description: Verify that mobile requests presenting an `X-App-Version` header lower than the configured port minimum are refused.
- Preconditions: Port profile setting `min_app_version = "2.4.0"`.
- Test Steps:
  1. Send `POST /api/v1/auth/mobile/login` with header `X-App-Version: 2.1.0`.
  2. Payload: `{"username": "pilot.tarek", "password": "PilotPass123!", "platform": "ANDROID"}`.
- Expected Result: HTTP 426 APP_UPDATE_REQUIRED. Problem body contains `code = "APP_UPDATE_REQUIRED"`, `min_app_version: "2.4.0"`, `detail = "This version of the app is no longer supported. Update the app to continue."`.
- Negative / Edge Cases Covered: Ensures backward incompatible clients are barred from mutating data.
- Required Evidence: HTTP 426 status and `min_app_version` response member.

### TC-02-016: Public System Info Endpoint Availability
- Description: Verify that `GET /api/v1/system/info` responds publicly without authentication to provide port connectivity, name, and minimum version.
- Preconditions: Port profile configured for Damietta Port (`port_code = "EGDAM"`).
- Test Steps:
  1. Send `GET /api/v1/system/info` with no credentials or session cookies.
- Expected Result: HTTP 200 OK. Body contains: `port_id: 1`, `port_code: "EGDAM"`, `port_name: "Damietta Port"`, `timezone: "Africa/Cairo"`, `min_app_version: "2.4.0"`.
- Negative / Edge Cases Covered: Endpoint never checks user auth and never returns 426.
- Required Evidence: HTTP 200 response JSON.

### TC-02-017: UI Web Login Screen (P-16) Authentication Flow
- Description: Verify the end-to-end user experience on screen P-16 Port Login, including input validation, loading indicators, error banner display, and navigation.
- Preconditions: Browser opened to application root `/login`.
- Test Steps:
  1. Enter invalid credentials and click Submit. Verify error banner with localized Arabic text.
  2. Enter valid credentials and click Submit.
- Expected Result: Error banner renders correctly on failure. On success, button enters loading state, cookie is stored, and user is redirected to Home Dashboard (P-17).
- Negative / Edge Cases Covered: Client-side required field checks before dispatching HTTP request.
- Required Evidence: Browser screenshots of error state and successful redirect.

### TC-02-018: UI Forced Password Change Modal Flow
- Description: Verify that when an authenticated user has `must_change_password = true`, a non-dismissible modal intercepts navigation and mandates password reset.
- Preconditions: User signed in with temporary password.
- Test Steps:
  1. Observe that modal overlay covers screen and background click or Esc key does not close it.
  2. Enter matching valid new password and submit.
- Expected Result: Form submits, success toast appears, modal closes, and full app shell navigation is unlocked.
- Negative / Edge Cases Covered: Browser reload keeps modal visible until password is confirmed changed.
- Required Evidence: UI screenshots of locked modal and unlocked dashboard.

### TC-02-019: UI Mobile Tablet Login Screen (P-52) Flow
- Description: Verify that the tablet login screen displays port identification, supports username/password entry, and gracefully informs user if network is offline.
- Preconditions: Flutter tablet application installed.
- Test Steps:
  1. Launch app in airplane mode. Verify connection banner indicates offline mode.
  2. Re-enable network, submit credentials.
- Expected Result: Connection status updates, login succeeds, Bearer token stored securely in Hive encrypted storage, user lands on task screen (P-54).
- Negative / Edge Cases Covered: Network recovery during authentication attempt.
- Required Evidence: Tablet screen capture of login screen and authenticated state.

### TC-02-020: UI App Update Required Screen (P-57) Blocking
- Description: Verify that when the server returns 426, the mobile app navigates to P-57 App Update Required, blocking all operations while preserving pending Outbox data.
- Preconditions: Tablet app with simulated version 2.1.0 and 2 pending Outbox events.
- Test Steps:
  1. Attempt login or sync.
  2. Receive HTTP 426.
- Expected Result: Screen P-57 displays "App Update Required" with minimum version 2.4.0. Navigation bar is disabled. Local Outbox records in Hive storage remain intact and unpurged.
- Negative / Edge Cases Covered: Outbox preservation during mandatory client upgrade.
- Required Evidence: Screenshot of P-57 screen and Hive box inspect log showing 2 retained records.
