## Detailed Test Cases

### TC-01-001: AI Subsystem Architectural Isolation Verification
- Description: Verify the critical architectural invariant that the AI subsystem exposes NO direct public REST API to external clients or web browsers. All interactions must strictly flow through Redis job queues (`queue:part1`, `queue:part2`, etc.) and MySQL persistence tables per contracts/qa/ai-testing-guide.md.
- Preconditions: Full platform environment running (Backend, AI workers, Nginx reverse proxy).
- Test Steps:
  1. Attempt to send public HTTP requests directly to AI worker ports or endpoints (e.g. `POST /api/v1/ai/solve`, `POST http://localhost:8001/recommend`).
  2. Inspect Nginx routing configuration and network firewall rules.
- Expected Result: External HTTP requests return HTTP 404 Not Found or Connection Refused. Nginx exposes only `/api/v1` routes handled by Laravel monolith. AI workers run as background Python daemons with no external ingress.
- Negative / Edge Cases Covered: Probing for undocumented internal API endpoints.
- Required Evidence: Network port scan log and HTTP 404 response payload.

### TC-01-002: Schema-Compliant Job Envelope Processing (CT-08)
- Description: Verify that a valid AI job pushed to Redis by the Backend adhering to the CT-08 outer envelope schema is successfully received, unpacked, and parsed by the designated Python worker.
- Preconditions: AI Part 1 worker active and listening on `queue:part1`.
- Test Steps:
  1. Push a JSON message to Redis `queue:part1` using `RPUSH`:
     ```json
     {
       "contract_version": "1.0",
       "job_type": "PART1_RUN",
       "job_id": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d",
       "run_id": 101,
       "enqueued_at": "2026-11-02T08:00:00.000000Z",
       "triggered_by_user_id": 41,
       "payload": {
         "berthing_request_id": 205,
         "reason": "CUSTOMS_APPROVAL"
       }
     }
     ```
  2. Monitor worker log and Redis queue status.
- Expected Result: Message is dequeued via `BLPOP`. Worker logs successful envelope validation against `envelope.schema.json`. Job execution starts for `run_id = 101`.
- Negative / Edge Cases Covered: Validates required top-level members and contract version "1.0".
- Required Evidence: Redis queue length reduction and AI worker execution log.

### TC-01-003: Malformed Job Envelope Rejection
- Description: Verify that an invalid or malformed message pushed to a worker queue (e.g., missing `job_id`, wrong `contract_version`, or extraneous properties) is safely rejected without crashing the worker process.
- Preconditions: AI worker active on `queue:part1`.
- Test Steps:
  1. Push malformed JSON envelope to `queue:part1`:
     ```json
     {
       "contract_version": "99.0",
       "job_type": "UNKNOWN_JOB",
       "payload": {}
     }
     ```
  2. Check worker process status after 5 seconds.
- Expected Result: Worker detects schema violation, logs error with category `INVALID_ENVELOPE`, discards malformed message, and remains running in healthy listening state.
- Negative / Edge Cases Covered: Worker resilience against queue corruption or malformed payloads.
- Required Evidence: Worker error log showing schema rejection and proof of process liveness.

### TC-01-004: Idempotent Run Claim under Competing Workers
- Description: Verify that when multiple worker instances consume jobs from the same queue, job claiming is strictly idempotent and atomic via database row lock (`UPDATE forecast_runs SET status='RUNNING' WHERE id=? AND status='QUEUED'`).
- Preconditions: Two Part 1 worker instances running concurrently. Database record `forecast_runs` id 105 has `status = "QUEUED"`.
- Test Steps:
  1. Enqueue job for `run_id = 105`.
  2. Simulate concurrent claim attempt by Worker A and Worker B.
- Expected Result: Exactly one worker obtains 1 updated row and proceeds with execution. The other worker obtains 0 updated rows and safely ignores the job. Zero duplicate calculations performed.
- Negative / Edge Cases Covered: Race condition prevention on shared Redis queues.
- Required Evidence: Database query snapshot showing single transition to `RUNNING` and worker log outputs.

### TC-01-005: AI Database Write Ownership Enforcement (CT-15)
- Description: Verify the strict architectural write ownership boundary: AI workers must write only to their designated run and result tables, and must NEVER update entity status columns owned by the Backend monolith.
- Preconditions: AI Part 1 job executing for `berthing_request_id = 205`.
- Test Steps:
  1. Worker finishes calculation.
  2. Inspect MySQL tables `forecast_runs`, `forecast_windows`, and `berthing_requests`.
- Expected Result: Worker inserts/updates `forecast_runs` and `forecast_windows`. Worker DOES NOT modify `berthing_requests.status` directly. `berthing_requests.status` remains unchanged until the Backend processes the C-06 completion message.
- Negative / Edge Cases Covered: Prevents split-brain state mutations between Python workers and Laravel monolith.
- Required Evidence: MySQL query results before and after worker commit confirming column ownership boundaries.

### TC-01-006: Successful Job Completion Signaling (CT-14 / C-06)
- Description: Verify that upon successful calculation, the worker publishes a schema-compliant C-06 completion message to `queue:c06`.
- Preconditions: AI worker executing job with `job_id = "job-xyz-123"` and `run_id = 101`.
- Test Steps:
  1. Allow worker calculation to complete.
  2. Read message from Redis `queue:c06`.
- Expected Result: Message is present on `queue:c06` conforming to `c06-completion.schema.json`:
  ```json
  {
    "contract_version": "1.0",
    "job_id": "job-xyz-123",
    "run_id": 101,
    "job_type": "PART1_RUN",
    "status": "DONE",
    "outcome": "FEASIBLE",
    "error_category": null,
    "completed_at": "2026-11-02T08:00:10.123456Z"
  }
  ```
- Negative / Edge Cases Covered: `error_category` is strictly null when `status = "DONE"`.
- Required Evidence: JSON message extracted from `queue:c06`.

### TC-01-007: Unhandled Exception and Error Categorization
- Description: Verify that when an AI worker encounters a runtime solver error or unhandled condition, it commits `status = "FAILED"` to the run table and emits a C-06 message with an approved `error_category`.
- Preconditions: Simulated database disconnection or solver failure during Part 2 solve.
- Test Steps:
  1. Trigger Part 2 solve with invalid solver parameters causing exception.
  2. Monitor `queue:c06`.
- Expected Result: C-06 message emitted with: `status: "FAILED"`, `error_category: "SOLVER_ERROR"` (one of `INVALID_ENVELOPE`, `PRECONDITION_FAILED`, `DATA_UNAVAILABLE`, `CONFIGURATION_ERROR`, `SOLVER_ERROR`, `TIMEOUT`, `INTERNAL_ERROR`), `message` containing diagnostic text under 1000 characters.
- Negative / Edge Cases Covered: Diagnostic details never expose raw stack traces to end users.
- Required Evidence: C-06 failure payload and database run record marked FAILED.

### TC-01-008: Worker Heartbeat Emission over Redis (CT-16)
- Description: Verify that active AI worker daemons publish periodic heartbeat hashes to Redis every 15 seconds with a 60-second Time-To-Live (TTL).
- Preconditions: EDI, Part 1, Part 2, and Yard workers running.
- Test Steps:
  1. Inspect Redis keys `worker:health:edi`, `worker:health:part1`, `worker:health:part2`, `worker:health:yard`.
  2. Verify hash fields: `worker_id`, `worker_version`, `status`, `last_heartbeat_at`, `current_job_id`.
  3. Verify key TTL using Redis `TTL worker:health:part1`.
- Expected Result: Keys exist, `status` is `IDLE` or `PROCESSING`, `last_heartbeat_at` is within the last 15 seconds, and key TTL is between 45 and 60 seconds.
- Negative / Edge Cases Covered: Heartbeat keeps refreshing automatically during long-running jobs.
- Required Evidence: Redis HGETALL command output and TTL check for each worker.

### TC-01-009: Worker DOWN State Detection on Heartbeat Silence
- Description: Verify that the Backend health monitor flags an AI worker as `DOWN` and raises an alert when its Redis heartbeat has not refreshed for more than 120 seconds (2 minutes).
- Preconditions: Stop Part 2 worker process (`SIGSTOP` or container pause).
- Test Steps:
  1. Wait for 65 seconds until Redis TTL expires key.
  2. Wait for 125 seconds.
  3. Query health monitoring status service in Backend.
- Expected Result: Backend health service marks `worker:part2` status as `DOWN`. Operational log records worker failure alert per CT-16 / DEC-10.
- Negative / Edge Cases Covered: Distinction between `DEGRADED` (45-120 s) and `DOWN` (>120 s).
- Required Evidence: Backend health monitor status output and alert log entry.

### TC-01-010: Stale Run Sweeper Execution
- Description: Verify that the Backend sweeper detects runs remaining in `RUNNING` status longer than `run_stale_after_seconds` and marks them `FAILED` with category `TIMEOUT`.
- Preconditions: Orphaned run in `forecast_runs` with `status = "RUNNING"` and `started_at` 30 minutes in the past.
- Test Steps:
  1. Execute Backend sweeper command: `php artisan port:sweep-stale-runs`.
  2. Inspect database record.
- Expected Result: Run record updated to `status = "FAILED"`, `error_category = "TIMEOUT"`, `finished_at = CURRENT_TIMESTAMP`.
- Negative / Edge Cases Covered: Prevents hanging runs from indefinitely locking active keys.
- Required Evidence: SQL query showing run status transitioned from RUNNING to FAILED.

### TC-01-011: Synchronous Validation Worker Roundtrip (CT-13)
- Description: Verify that synchronous rule checks dispatched by Backend on `queue:validate` (for user override or correction validation) are evaluated by the validation worker and returned within 15 seconds.
- Preconditions: Validation worker active and listening on `queue:validate`.
- Test Steps:
  1. Dispatch validation request with unique `correlation_id` and payload.
  2. Await response on temporary reply queue or correlation channel.
- Expected Result: Response received within 15 seconds containing `is_valid: true/false`, list of violation codes, and execution duration. Result cached with TTL 600s.
- Negative / Edge Cases Covered: Timeout handling if validation exceeds 15-second budget.
- Required Evidence: Request and response timestamp log demonstrating <15s turnaround.

### TC-01-012: Reference Scale Seeder Execution (P1-B6)
- Description: Verify that executing the platform database seeder (`DatabaseSeeder`) populates the full Damietta reference port scale: exactly 8 terminals and 36 berths with realistic physical dimensions.
- Preconditions: Clean MySQL database schema migrated via CT-17 migrations.
- Test Steps:
  1. Run seeder command: `php artisan db:seed --class=DamiettaPortSeeder`.
  2. Execute verification queries:
     - `SELECT count(*) FROM terminals;`
     - `SELECT count(*) FROM berths;`
- Expected Result: Exactly 8 rows in `terminals` (DCT, DGT, DBT, DLT, DGC2, DRT, DGT3, DMT). Exactly 36 rows in `berths` with valid lengths, depths, and LOA limits. Zero foreign key constraint failures.
- Negative / Edge Cases Covered: Seeder idempotency (running twice does not create duplicates).
- Required Evidence: SQL query output showing 8 terminals and 36 berths.

### TC-01-015: Internal AI FastAPI Service Authorization (AI-F01)
- Description: Verify that the internal AI FastAPI HTTP service enforces the `X-Service-Token` header for service-to-service communication, rejecting unauthorized internal calls.
- Preconditions: AI FastAPI service running on internal port 8001.
- Test Steps:
  1. Send `GET http://localhost:8001/internal/health` without headers.
  2. Send `GET http://localhost:8001/internal/health` with header `X-Service-Token: valid-internal-secret`.
- Expected Result: Step 1 returns HTTP 401 Unauthorized. Step 2 returns HTTP 200 OK with service status.
- Negative / Edge Cases Covered: Protects internal diagnostic and evaluation endpoints from unauthorized cluster access.
- Required Evidence: HTTP 401 and HTTP 200 responses.
