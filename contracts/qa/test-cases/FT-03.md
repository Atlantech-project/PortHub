## Detailed Test Cases

### TC-03-001: Port Admin Role Authorization on Administrative Routes
- Description: Verify that users with the `PORT_ADMIN` role have complete authorization to access user management, role assignments, and device administration endpoints.
- Preconditions: Signed-in session for user `admin.karim` with role `PORT_ADMIN`.
- Test Steps:
  1. Send `GET /api/v1/users` with Port Admin session.
  2. Send `GET /api/v1/audit-logs` with Port Admin session.
- Expected Result: HTTP 200 OK for both endpoints. Response contains requested administrative collections with pagination metadata.
- Negative / Edge Cases Covered: Access permitted across all port-wide resources.
- Required Evidence: HTTP 200 response headers and JSON data payload.

### TC-03-002: Unauthorized Role Access to Administrative Routes
- Description: Verify that non-administrative roles (e.g., `PORT_STAFF`, `PILOT`, `BERTH_PLANNER`) are forbidden from accessing administrative endpoints.
- Preconditions: Signed-in session for user `staff.ahmed` with role `PORT_STAFF`.
- Test Steps:
  1. Send `POST /api/v1/users` with `PORT_STAFF` session.
  2. Payload: `{"username": "new.staff", "name": "New Staff", "role": "PORT_STAFF"}`.
- Expected Result: HTTP 403 FORBIDDEN. Problem body contains `code = "FORBIDDEN"`, `message_key = "errors.forbidden"`, `detail = "You do not have permission to perform this action."`.
- Negative / Edge Cases Covered: Enforces RBAC boundary across all non-admin roles.
- Required Evidence: HTTP 403 response payload.

### TC-03-003: Field Role Web Navigation Barrier (DEC-48)
- Description: Verify that field personnel with mobile roles (e.g. `PILOT`, `TUG_MASTER`) attempting to log into or navigate the web dashboard are blocked and redirected to screen P-20 Access Denied per DEC-48.
- Preconditions: Active user `pilot.tarek` with role `PILOT`.
- Test Steps:
  1. Sign in via web login form `/login` as `pilot.tarek`.
  2. Observe frontend router navigation behavior.
- Expected Result: Router guard detects field role. Navigation redirects to screen P-20 Access Denied displaying message: "This role is restricted to tablet operations. Please sign in via the port tablet application."
- Negative / Edge Cases Covered: Web URL direct bookmark navigation attempt by field role.
- Required Evidence: Browser screenshot of P-20 screen with tablet guidance notice.

### TC-03-004: Cross-Terminal Tenant Isolation Enforcement
- Description: Verify tenant isolation between terminal operators: an operator assigned to Terminal A attempting to access private or commercial records of Terminal B receives HTTP 404 Not Found (not 403) to prevent resource existence disclosure.
- Preconditions:
  - User `operator.damietta_ct` assigned exclusively to Terminal 1 (`DCT`).
  - Terminal 2 (`DGT`) possesses private terminal asset or commercial record ID 805.
- Test Steps:
  1. Sign in as `operator.damietta_ct`.
  2. Send `GET /api/v1/terminals/2/private-resources/805`.
- Expected Result: HTTP 404 NOT_FOUND. Problem body contains `code = "NOT_FOUND"`, `message_key = "errors.not_found"`. No data leaked regarding Terminal 2 existence of ID 805.
- Negative / Edge Cases Covered: Multi-tenant boundary isolation between competing terminal operating companies within the port.
- Required Evidence: HTTP 404 response payload.

### TC-03-005: Sequential Write Chain Evaluation Order
- Description: Verify that all state-changing endpoints evaluate authorization, safety, versioning, and validation checks in the strict architectural sequence defined in CT-01: 401 -> 403 -> 426 -> 423 -> 409 -> 422.
- Preconditions: Multiple invalid conditions prepared simultaneously on a single mutating request.
- Test Steps:
  1. Prepare request with invalid auth, wrong role, and malformed body: verify HTTP 401 is returned first.
  2. Prepare request with valid auth, forbidden role, and malformed body: verify HTTP 403 is returned second.
  3. Prepare request with valid auth, allowed role, stale version token, and invalid business rule: verify HTTP 409 is returned before HTTP 422.
- Expected Result: Refusal matches the earliest failing check in the chain on every request without short-circuiting incorrectly.
- Negative / Edge Cases Covered: Eliminates inconsistent error ordering across controllers.
- Required Evidence: Sequence of HTTP responses demonstrating exact ordering compliance.

### TC-03-006: Optimistic Concurrency Control (OCC) Version Conflict
- Description: Verify that updating a record with a stale `version` token returns HTTP 409 Conflict and includes the current stored database version in the problem body.
- Preconditions: User record 45 exists in database with `version = "2026-11-01T10:00:00.000000Z"`.
- Test Steps:
  1. Client A reads user 45 and receives version `"2026-11-01T10:00:00.000000Z"`.
  2. Client B updates user 45, advancing database version to `"2026-11-01T10:05:00.000000Z"`.
  3. Client A attempts to update user 45 sending original version `"2026-11-01T10:00:00.000000Z"`.
  4. Payload: `{"name": "Updated Name", "version": "2026-11-01T10:00:00.000000Z"}`.
- Expected Result: HTTP 409 VERSION_CONFLICT. Response body contains:
  ```json
  {
    "type": "https://atlantech.io/errors/version-conflict",
    "title": "Record changed",
    "status": 409,
    "code": "VERSION_CONFLICT",
    "message_key": "errors.version_conflict",
    "detail": "This record was changed by another user. Reload it and apply your changes again.",
    "current": {
      "id": 45,
      "version": "2026-11-01T10:05:00.000000Z"
    }
  }
  ```
- Negative / Edge Cases Covered: Opaque string comparison preventing millisecond truncation bugs.
- Required Evidence: HTTP 409 JSON body with `current` object.

### TC-03-007: Mutating Request under License READ_ONLY Mode
- Description: Verify that when the port license is in READ_ONLY mode (e.g. billing grace period expired), all entity creation, modification, and deletion attempts are locked with HTTP 423.
- Preconditions: Database table `license_states` configured with `mode = "READ_ONLY"`. User signed in as Port Admin.
- Test Steps:
  1. Send `POST /api/v1/users` with payload to create a new user.
  2. Send `POST /api/v1/users/45/deactivate` to update user state.
- Expected Result: HTTP 423 LICENSE_READ_ONLY on both requests. Problem body:
  ```json
  {
    "type": "https://atlantech.io/errors/license-read-only",
    "title": "License is read-only",
    "status": 423,
    "code": "LICENSE_READ_ONLY",
    "message_key": "errors.license_read_only",
    "detail": "The port license is read-only: you can view data, but changes are blocked. Contact your port administrator."
  }
  ```
- Negative / Edge Cases Covered: Blocks writes across all modules without corrupting state.
- Required Evidence: HTTP 423 problem JSON response.

### TC-03-008: Permitted Operations under License READ_ONLY Mode
- Description: Verify that when license is READ_ONLY, read-only queries (GET) and emergency safety alerts remain operational.

  2. Send `GET /api/v1/audit-logs`.
  3. Send `GET /api/v1/system/info`.
- Expected Result: HTTP 200 OK for all read endpoints. Query responses return normally.
- Negative / Edge Cases Covered: Read-only access to operational history is maintained during license lockout.
- Required Evidence: HTTP 200 responses with data payloads.

### TC-03-009: User Creation with Temporary One-Time Password
- Description: Verify that a Port Admin can create a new staff account, automatically generating a temporary one-time password and setting `must_change_password = true`.

### TC-03-010: User Creation with Duplicate Username
- Description: Verify that attempting to create an account with an existing username returns validation failure.
- Preconditions: User `staff.ahmed` already exists in database.
- Test Steps:
  1. Send `POST /api/v1/users` with payload `{"username": "staff.ahmed", "name": "Duplicate Ahmed", "role": "PORT_STAFF"}`.
- Expected Result: HTTP 422 VALIDATION_FAILED. Errors dictionary contains `"username": ["validation.unique"]`.
- Negative / Edge Cases Covered: Case-insensitive collision detection (`staff.ahmed` vs `STAFF.AHMED`).
- Required Evidence: HTTP 422 JSON error response.

### TC-03-011: User Deactivation under Row Lock
- Description: Verify that a Port Admin can deactivate an active staff member, locking the database row during update and terminating active sessions.
- Preconditions: Active user `staff.marwa` (`id = 60`, `is_active = true`).
- Test Steps:
  1. Send `POST /api/v1/users/60/deactivate`.
  2. Verify response status.
  3. Attempt API request using previous session of `staff.marwa`.
- Expected Result: HTTP 200 OK. User record updated to `is_active = 0`. Step 3 returns HTTP 403 ACCOUNT_DISABLED immediately.
- Negative / Edge Cases Covered: Immediate session revocation in Redis/Sanctum upon database deactivation.
- Required Evidence: HTTP 200 response, SQL record verification, and subsequent 403 error.

### TC-03-012: Self-Deactivation Prevention by Administrator
- Description: Verify that a Port Admin cannot deactivate their own user account.
- Preconditions: Signed-in Port Admin `admin.karim` (`id = 10`).
- Test Steps:
  1. Send `POST /api/v1/users/10/deactivate` with session of `admin.karim`.
- Expected Result: HTTP 409 Conflict. Problem body contains `code = "SELF_DEACTIVATION_PROHIBITED"`, `detail = "Administrators cannot deactivate their own accounts."`. Database row remains `is_active = 1`.
- Negative / Edge Cases Covered: Prevents accidental administrative lockout.
- Required Evidence: HTTP 409 response and unmodified database row.

### TC-03-013: Last Port Admin Deactivation Protection
- Description: Verify that the system prohibits deactivating the sole remaining active Port Admin under concurrent requests.
- Preconditions: Exactly one active user with role `PORT_ADMIN` exists in system (`admin.sole`, `id = 1`). Second user is Port Director attempting admin maintenance.
- Test Steps:
  1. Attempt deactivation of user 1: `POST /api/v1/users/1/deactivate`.
- Expected Result: HTTP 409 Conflict. Body contains `code = "LAST_ADMIN_PROTECTION"`, `detail = "The last remaining port administrator cannot be deactivated."`.
- Negative / Edge Cases Covered: Row-lock guarded check prevents race conditions when two admins attempt mutual deactivation.
- Required Evidence: HTTP 409 response payload and system count query confirming active admin retained.

### TC-03-014: Role Assignment with History Tracking (DEC-36)
- Description: Verify that assigning a new role to a user terminates their prior active assignment with an `active_to` timestamp and inserts a new active assignment per DEC-36.

  - New row created for `BERTH_PLANNER` with `active_from = CURRENT_TIMESTAMP(6)` and `active_to = null`.
- Negative / Edge Cases Covered: Audit preservation of all historical user permissions.
- Required Evidence: SQL query result showing prior row closed and new row active.

### TC-03-019: Transactional Audit Log Generation on Mutation
- Description: Verify that every state-changing database write automatically commits a corresponding row in `audit_logs` in the identical atomic database transaction.
- Preconditions: Port Admin signed in.
- Test Steps:
  1. Send `POST /api/v1/users` to create a user.
  2. Inspect database `audit_logs` table for the transaction.
- Expected Result: Database contains audit row recording: `user_id` of acting admin, `action = "USER_CREATED"`, `entity_type = "user"`, `entity_id = <new_user_id>`, `new_values` JSON snapshot, and timestamp.
- Negative / Edge Cases Covered: If user creation fails or rolls back, zero audit records are orphaned.
- Required Evidence: Database query snapshot showing synchronized transaction commit.

### TC-03-020: Refused Write Logged as REJECTED_ATTEMPT
- Description: Verify that unauthorized or rejected state mutation attempts are captured in the audit log as `REJECTED_ATTEMPT` with the refusal reason code.
- Preconditions: User signed in as `PORT_STAFF`.
- Test Steps:
  1. Attempt unauthorized user deletion: `POST /api/v1/users/45/deactivate`.
  2. Inspect database `audit_logs` table.
- Expected Result: Request returns HTTP 403. Database `audit_logs` contains row with `action = "REJECTED_ATTEMPT"`, `actor_id = <staff_id>`, `target_entity = "user"`, `target_id = 45`, `reason_code = "FORBIDDEN"`.
- Negative / Edge Cases Covered: Security compliance monitoring for intrusion or unauthorized probing.
- Required Evidence: SQL query record showing `REJECTED_ATTEMPT` audit entry.
